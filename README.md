# frontieror-routing

Practice solvers for the routing, scheduling and network-design problems of the [FrontierOR Challenge](https://frontieror-challenge.com/), built and calibrated on public benchmark instances by MV2 of Munim, Inc.

Made with AI agents working in MV2's name. License: Apache-2.0 (code); notes and numbers CC BY 4.0.

**The contest contract.** Each solver follows the FrontierOR Main-track contract (`python solve.py --problem <slug> --instance in.json --output out.json --time-limit 60`): Python only, no network, 2 vCPUs, and it stops a few seconds before the limit.

**How each solver is calibrated:**
- it is run as a subprocess, the same way the contest sandbox does;
- every solution is re-checked by an independent checker in the harness, and on the public FrontierOR instances also by the task's official `feasibility_check.py`;
- the benchmark instances are downloaded at run time from their own repositories at pinned commits. They are not copied here; only our own numbers (and, where useful for re-checking, our own solutions) are.

Guesses about each run are written down before it runs and scored afterwards, including the ones that fail. From 2026-11-13, each graded job first waits until its guesses are public here and records whether they were (`wait_prereg.py`). This rule came in after one run's guesses went public six minutes after the run ended ([census/score-v2.md](census/score-v2.md)).

These are practice solvers. They are not an official FrontierOR baseline. Scores below follow the contest's rule ([scoring](https://frontieror-challenge.com/docs/main/scoring)): when minimising positive costs, reference / ours; when both are negative, ours / reference; better with the opposite sign scores 2; every score is capped at 2. The reference here is the Gurobi answer stored with the benchmark's public instances, usually stopped at a one-hour limit. The contest scores private instances against its own frozen best-known values.

## What the calibration runs have shown so far

- **Exact sub-problems inside a heuristic win.** In each case below, the heuristic fixes part of the answer and solves the rest exactly:
  - guo2021: once patients are placed, each room's cancellations in each scenario are a small knapsack solved exactly, so the search compares plans on their true expected cost. In 60 s that beat one hour of Gurobi on the deterministic-equivalent model on all 5 large instances.
  - he2020: once a route's customer order is fixed, its best schedule is an isotonic regression solved exactly. That beat a one-hour Gurobi run on 4 of 5 large instances in 60 s.
  - fischetti1997: once the cluster order is fixed, the best node in every cluster comes from an exact dynamic programme. In 60 s that matched or beat one hour of Gurobi on 3 of 5 large instances.
  - Stochastic facility location: once the open set is fixed, the problem splits into one min-cost flow per scenario.
- **Big stochastic models leave the most room.** Where the benchmark's model is a scenario-expanded deterministic equivalent with hundreds of thousands of binaries (guo2021), Gurobi's one-hour answer can be far from good. A heuristic that prices the scenarios exactly gains the most there.
- **Coverage first.** In a contest where no output scores 0, a solver that always writes a checked, feasible answer matters more than a better one that sometimes writes nothing. Set partitioning is the example: a branch-and-cut that proves optimality in minutes wrote nothing in 60 s on a wide instance, until v0.2.0 found a feasible solution first.
- **Read the description as well as the schema.** On three tasks, `instance_schema.json` misses something the instances carry and the checker enforces: zetina2020's MaxCut form, rothenbacher2018's customer time windows, and legrain2024's hard limits ([drift score](census/drift-score-v1.md)). A public instance that fails zeroes the whole problem in the contest.
- **Read the official checker, then run it.** Reading code finds candidates; only running them settles them. We suspected he2020's checker of using rho = 0, because it reads a key the schema does not list. The run showed that every instance carries that key with the right value, so there was no gap ([score](he2020/score-v1.md)). The census confirmed the vidal2011 one by running it.
- **Re-score stored references before comparing with them.** In OPLib, 7 stored EA4OP routes earn their stated score only on the instance files as they were before a 2020 fix ([score-2](oplib-audit/score-2.md)). In FrontierOR, every stored Gurobi verdict we re-ran (897 cases) reproduces.
- **Your harness can be the bug.** 28 "checker failures" in the census were our own: some FrontierOR checkers import modules shipped next to them, and we had fetched only the checker. pecin2017's first run failed on our own version-print line.
- **Pin and read the API of the version you install.** PyVRP 0.14 changed how coordinates are passed, and an early VRPDDP version silently ran without them.
- **Host pauses:** runs reported as over time coincided with the host freezing the container, not with the solver. Harnesses now detect a freeze and re-run the instance.
- **Other things the official checkers decide:**
  - barnhart2000 prices a rejected commodity at `artificial_arc_cost x demand`.
  - bard2002 does not time the depot legs.
  - gangammanavar2020 and xie2019 regenerate part of the data from a seed, so a solver has to replay the same generator to know its own objective.
  - cordeau2019's answer must cover exactly the instance's `problem_types`, a key the instance schema does not list.
  - guo2021 checks that the stated objective is within 0.5% of the best recourse for the submitted first stage.
  - martin-iradi2024 requires the first call's arrival only to be no later than its start, while the stored Gurobi model fixes it to the earliest start time.
  - nagy2015 forbids an arc from a customer's pickup node straight to its own delivery node (constraint 15), even though the two are at the same place.
